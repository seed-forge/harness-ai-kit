# 6 信号评分模型

用于量化判定一个 session 中的重复模式是否值得提炼为 Loop。对每个信号独立打分，累加后根据阈值做出决策。

---

## 信号定义

| 信号编号 | 信号名称 | 分值 | 判定条件 | 证据来源 |
|----------|----------|------|----------|----------|
| S1 | 重复模式 | +2 | 同一操作序列在 session 中出现 ≥ 2 次 | workflow-session.json 中 task 记录、summaries 中重复步骤描述 |
| S2 | 明确输入输出 | +1 | 可以从 session 资产中识别出清晰的输入格式和输出格式 | SKILL.md 的 input/output 章节、summaries 中的文件列表 |
| S3 | 验收可验证 | +1 | 成功或失败能被客观验证，不依赖主观感受 | convergence.criteria、测试通过率、lint 检查结果 |
| S4 | 存在触发事件 | +1 | 存在明确的触发条件（时间、事件、状态变化）触发该模式 | workflow 触发器、CI webhook、定时任务配置 |
| S5 | 不依赖临场判断 | +1 | 模式中的关键决策点可以被规则化，不依赖人的即时判断 | 工作流中无"根据经验判断""视情况而定"等模糊步骤 |
| S6 | 未来复现 | +1 | 基于 session 上下文判断，该模式在未来很可能再次出现 | session topic 的持续性质、业务线的重复需求 |

---

## 评分计算

```
total_score = S1 + S2 + S3 + S4 + S5 + S6
            = (0 or 2) + (0 or 1) + (0 or 1) + (0 or 1) + (0 or 1) + (0 or 1)
            = 0 ~ 7 分
```

**S1（重复模式）是唯一双分信号**，因为它是最强的 Loop 候选指标。一个模式只出现一次，即使其他信号都满足，也不值得做成自动化 Loop。

---

## 阈值决策

| 总分区间 | 判定 | 行动 |
|----------|------|------|
| **≥ 5** | 强候选 | 自动生成 Loop 草案，进入提炼流程 |
| **3 ~ 4** | 弱候选 | 生成草案草稿，提示用户确认后决定是否继续 |
| **≤ 2** | 不建议 | 输出不提炼原因，建议保留为知识卡片或 SOP |

---

## 信号提取方法

### S1：重复模式识别

```
输入：workflow-session.json + .summaries/
方法：
  1. 提取 session 中所有 task 的操作序列
  2. 对操作序列做归一化（忽略文件路径等变量部分）
  3. 统计相同归一化序列的出现次数
  4. 出现次数 ≥ 2 → S1 = 2，否则 S1 = 0
```

**归一化示例**：
- `Read(src/auth/login.ts)` 和 `Read(src/auth/logout.ts)` 归一化为 `Read(src/auth/*.ts)`
- 如果两者都出现在不同 task 中，视为同一模式重复

### S2：输入输出识别

```
输入：SKILL.md 的 input/output 章节 + summaries 中的文件列表
方法：
  1. 检查 SKILL.md 是否有明确的 input 章节且列出 ≥ 1 项
  2. 检查 SKILL.md 是否有明确的 output 章节且列出 ≥ 1 项
  3. 或检查 summaries 中是否有清晰的"Files Modified"和"Content Added"
  4. 两者都有 → S2 = 1，否则 S2 = 0
```

### S3：验收可验证性

```
输入：convergence.criteria / acceptance criteria / test results
方法：
  1. 查找 session 中是否有量化的验收标准
  2. 如 tests_pass_rate、coverage_pct、error_count 等
  3. 或查找是否有明确的 pass/fail 判断逻辑
  4. 存在可量化或可二元判定的验收标准 → S3 = 1，否则 S3 = 0
```

### S4：触发事件识别

```
输入：workflow 配置、触发器定义、session 启动条件
方法：
  1. 检查 session 是否由明确事件触发（CI failure、定时任务、用户命令）
  2. 检查 workflow-session.json 中是否有触发条件描述
  3. 存在明确触发事件 → S4 = 1，否则 S4 = 0
```

### S5：临场判断依赖评估

```
输入：workflow 步骤描述、summaries 中的判断记录
方法：
  1. 扫描 workflow 步骤中是否有模糊判断语句
  2. 如"根据实际情况决定""凭经验判断""视情况而定"
  3. 扫描 summaries 中是否有大量人工决策记录
  4. 关键步骤均可被规则化 → S5 = 1，否则 S5 = 0
```

### S6：未来复现概率

```
输入：session topic、业务线性质、历史 session 记录
方法：
  1. 检查 session topic 是否为持续性主题（如 CI、部署、运维）
  2. 检查历史 session 中是否有类似 topic
  3. 检查该 topic 是否属于稳定的业务线
  4. 未来很可能复现 → S6 = 1，否则 S6 = 0
```

---

## 评分报告格式

提炼时应输出评分报告：

```markdown
## 6 信号评分报告

| 信号 | 得分 | 依据 |
|------|------|------|
| S1 重复模式 | 2 | 同操作序列出现 5 次（task 3, 5, 7, 9, 11） |
| S2 明确输入输出 | 1 | SKILL.md 有 input/output 章节 |
| S3 验收可验证 | 1 | tests_pass_rate == 1.0 作为验收标准 |
| S4 存在触发事件 | 1 | CI webhook 触发 |
| S5 不依赖临场判断 | 1 | 所有步骤均可规则化 |
| S6 未来复现 | 1 | CI 修复为持续性需求 |

**总分：7/7 → 强候选**
```
