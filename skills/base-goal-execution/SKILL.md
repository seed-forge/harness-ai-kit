# Goal 驱动执行

## 用途

当 AI 制定计划（Plan）或执行已有计划时，本技能定义从"目标定义 → 任务拆解 → 逐步实现 → 质量门禁 → 交付确认"的完整闭环。
适用于 Qoder Plan 文件、手写任务清单、或任何需要多步执行的工程任务。

## 核心理念

> **每个任务必须有明确的验收标准，每次执行必须有可观测的进度，每个失败必须有结构化的恢复策略。**

借鉴来源：
- [goal-workflow](https://github.com/smallnest/goal-workflow) 的 Issue→Goal→Review→Ship 闭环
- Codex Goal 功能的目标驱动 + 检查点恢复模式
- Qoder 原生 Plan 体系的 `.md` 计划文件

## 触发条件

以下任一场景应自动激活本技能：

1. 用户要求"制定计划"、"做一个方案"、"规划一下"
2. AI 通过 `CreatePlan` 工具生成了计划文件
3. 用户要求执行某个已有的计划文件（如 Qoder 缓存的 `.md` 计划）
4. 用户说"继续上次的任务"、"恢复执行"
5. 任何涉及 3 个以上步骤的工程任务

## 执行框架

### Phase 0: Goal 定义（制定计划时）

制定计划时，必须包含以下结构：

```markdown
# [任务名称]

## 目标（Goal）
一句话描述最终交付物。

## 验收标准（Acceptance Criteria）
- [ ] AC-1: 具体可验证的条件
- [ ] AC-2: 具体可验证的条件
- [ ] ...

## 任务拆解（Tasks）
按依赖拓扑排序，每个任务包含：
- 任务 ID 和标题
- 输入 / 输出
- 验收标准（至少 1 条）
- 依赖关系（如有）

## 风险与约束
- 已识别的风险点
- 外部依赖或前置条件
```

**Goal 定义质量门禁**：
- 验收标准必须可验证（能运行命令、检查文件、观察行为）
- 每个任务的粒度应在单次会话中可完成
- 依赖关系必须显式声明，不允许隐式依赖

### Phase 1: 前置检查（Pre-flight）

执行前验证：

| 检查项 | 动作 |
|--------|------|
| 计划文件存在且完整 | 读取计划文件，确认 Goal + AC + Tasks 齐全 |
| 工作区状态清洁 | 检查是否有未提交变更可能冲突 |
| 依赖可用 | 确认所需的 CLI、MCP、技能、文件可访问 |
| 无循环依赖 | 验证任务依赖图无环 |

任一检查失败 → 停止执行，报告问题，等待用户确认。

### Phase 2: 逐步执行（Execution）

每个任务的执行循环：

```
读取任务 → 分析上下文 → 实现 → 验证 → 标记状态
```

**任务状态流转**：

```
pending → in_progress → done / failed / blocked / skipped
```

**执行纪律**：

1. **单任务聚焦**：同一时间只执行一个任务，完成后才进入下一个
2. **即时验证**：每个任务完成后立即验证其验收标准，不积攒到最后
3. **进度报告**：每完成一个任务，输出当前进度摘要
4. **变更隔离**：只修改当前任务直接相关的文件，不做"顺便"修改
5. **上下文保持**：执行中如需参考计划文件，重新读取而非依赖记忆

**进度报告格式**：

```
📊 进度: {done}/{total} ({percent}%)
  ✅ 完成: #{id1}, #{id2}
  🔄 进行中: #{id3}
  ⏭️  跳过: #{id4} ({reason})
  🔒 阻塞: #{id5} (依赖 #{id3})
  ❌ 失败: #{id6} ({error_type})
  📋 剩余: #{id7}, #{id8}
```

### Phase 3: 质量门禁（Review Gate）

所有任务执行完毕后，进入质量门禁：

1. **验收标准逐条核对**：逐条检查 Goal 的 Acceptance Criteria
2. **变更范围审查**：确认所有变更都在预期范围内
3. **回归检查**：确认修改未破坏已有功能（能运行测试时执行）
4. **文档同步**：如修改了公共接口或约定，更新相关文档

质量门禁不通过 → 回到 Phase 2 修复，最多 2 轮迭代。

### Phase 4: 交付确认（Delivery）

1. 输出最终交付报告
2. 逐条标注验收标准达成状态
3. 列出剩余风险或待跟进项
4. 等待用户确认

**交付报告模板**：

```markdown
## 交付报告

### Goal
{原始目标描述}

### 验收标准
- [x] AC-1: {描述} — ✅ 已验证: {验证方式}
- [x] AC-2: {描述} — ✅ 已验证: {验证方式}

### 变更摘要
- 文件 A: {变更说明}
- 文件 B: {变更说明}

### 剩余风险
- {风险描述及建议}

### 后续建议
- {如有}
```

## 错误恢复策略

任务执行失败时，按以下分类处理：

| 错误类型 | 恢复策略 | 最大重试 |
|---------|---------|---------|
| 构建/编译失败 | 读错误信息，修复代码，重新构建 | 3 |
| 测试失败 | 读测试输出，修复实现，重跑测试 | 3 |
| 依赖缺失 | 安装或配置缺失依赖 | 2 |
| 权限不足 | 停止，告知用户所需权限 | 0 |
| 网络/超时 | 等待 30s，重试 | 3 |
| 上下文丢失 | 重新读取计划文件和相关代码 | ∞ |
| 需求不清 | 停止，向用户提问澄清 | 0 |

**核心原则**：
- 不无限重试
- 不在未确认的情况下做破坏性操作
- 失败的任务保留现场供调查，不自动跳过

## 断点恢复

当用户说"继续上次的任务"或类似指令时：

1. 定位计划文件（Qoder 缓存路径或用户指定路径）
2. 读取计划文件，解析各任务状态
3. 检查已完成任务的变更是否仍然存在
4. 从第一个 `pending` 或 `in_progress` 任务继续
5. 输出恢复摘要后开始执行

## 与 Qoder Plan 的集成

Qoder 的 `CreatePlan` 工具生成的计划文件（如 `C:\Users\Working\AppData\Roaming\Qoder\SharedClientCache\cache\plans\*.md`）是本技能的输入源。

集成方式：
- **制定计划时**：按 Phase 0 的 Goal 定义结构组织计划内容
- **执行计划时**：从 Qoder 缓存读取计划文件，按 Phase 1-4 执行
- **计划更新时**：修改计划文件而非口头变更，保持文件为唯一真相源


## 推荐输出格式

执行完毕后输出极简回执：**状态**（✅ 成功 / ⚠️ 部分成功 / ❌ 失败）+ **关键结果**（1-2 行，如操作对象、产出位置、下一步）。无需强制套用大表格。

## 安全护栏

- 永远不在未确认的情况下删除文件或做不可逆操作
- 永远不在执行中修改与本 Goal 无关的代码
- 每个任务只修改预期内的文件
- 遇到需要超出原计划范围的变更时，停止并与用户确认
- 失败分支/变更保留供调查，不自动清理

## Human Decisions

> 结构化同源见 `decisions.yaml`；以下为人类可读汇总。

| # | 决策点 | 触发条件 | 选项 | 默认行为 |
|---|--------|---------|------|---------|
| HD-1 | 交付确认（Phase 4） | 所有任务执行完毕、进入交付阶段输出交付报告后 | 用户确认验收 / 退回修复未达标项 | 必问 |
| HD-2 | 超出原计划范围的变更 | 执行中遇到需要超出原 Goal 范围的变更时 | 停止并与用户确认扩展范围 / 维持原范围 | 必问 |
