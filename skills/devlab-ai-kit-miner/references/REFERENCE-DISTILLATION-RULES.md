# 沉淀决策规则与反模式

以下规则和反模式来自真实复盘 session，用于提高判断准确率。

## 规则 R1：先搜全再判断，避免"假阴性"

**教训**：初次搜索现有 skill 时，`Glob **/devlab-*` 只匹配到目录名而非目录下的 SKILL.md，误判为"无现有 devlab-* skill"，差点新建重复 skill。

**规则**：搜索现有资产时必须同时检查：
1. `ai-kit/skills/` 下所有目录名
2. 每个目录下的 `SKILL.md` 内容（至少读标题和用途段）
3. 关键词搜索（Grep 名称、库名、技术名词）

不要仅凭目录列表或 Glob 模式匹配就断言"不存在"。

## 规则 R2："补充"优先于"新增"

**判断规则**：
- 候选经验与现有资产的**主题域重叠 > 50%** → 补充
- 候选经验属于现有资产的**已定义章节**（如踩坑表、集成指南）→ 补充
- 候选经验涉及的**库/框架/技术栈相同** → 补充
- 只有当候选经验与所有现有资产 **完全不重叠**时 → 新增

## 规则 R3：版本兼容矩阵是高价值沉淀物

**信号**：
- `npm ls <package>` 显示同一依赖有多个主版本
- 报错信息与实际根因**跨层级**（如 Vite 报错，根因在 Astro 版本）
- 修复方案是**降级/锁定版本**而非代码修改

**规则**：优先沉淀为 `*-usage` 的独立章节或踩坑表条目。

## 规则 R4：症状链文档化

**规则**：当排查过程中出现**多个看似无关的报错最终归因于同一根因**时，必须记录完整症状链：
```
根因 → 第一症状（直接） → 第二症状（连锁） → 第三症状（误导性）
```
并标注哪些症状是**误导性的**（看似独立问题，实为连锁反应）。

## 规则 R5：代码即文档的边界

**判断规则**：当候选经验同时满足以下条件时，代码本身就是最好的文档，无需额外沉淀：
- 实现代码 < 200 行
- 只有 1 个使用方（当前项目）
- 没有踩坑过程（实现顺利，没有试错）
- 没有隐含的约束或陷阱

反之，如果实现过程中有**试错、踩坑、隐含约束**，即使代码量小也应沉淀。

## 反模式 A1：把一次性问题误判为可复用资产

**识别信号**：
- 触发条件需要**多个前提同时成立**
- 修复后无法在其他项目复现
- 没有稳定的输入/输出定义

**处理**：记录为知识卡片或合并到相关资产的踩坑表，不独立成资产。

## 反模式 A2：忽略 session 时间分配信号

**规则**：复盘时统计各阶段时间占比：
- 某个问题占 session 时间 **> 25%** → 强信号，优先评估沉淀
- 某个问题占 session 时间 **> 50%** → 必须沉淀
- 排查过程中**多次方向错误** → 说明缺乏诊断 SOP，沉淀价值更高

## 反模式 A3：把"项目特定实现"当"通用模式"

**识别信号**：
- 输入依赖私有数据结构
- 输出只在当前项目有意义
- 其他项目做类似事情时，参考价值 < 复制价值

**处理**：不沉淀。如果模式确实有通用性，应抽象为通用描述。

## 反模式 A4：团队共享资产混入项目特定路径

**识别信号**：
- 资产中出现 `src/islands/`、`@/` 等路径别名
- 函数名包含业务语义而非通用语义
- 文件名来自特定项目

**处理规则**：
- 引擎/模块：描述为"纯模块，可放在项目任意目录"
- 函数/API：使用通用命名
- 项目安装后由项目级配置补充具体路径
