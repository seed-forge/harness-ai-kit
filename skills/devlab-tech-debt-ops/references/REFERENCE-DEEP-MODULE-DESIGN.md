# REFERENCE-DEEP-MODULE-DESIGN — 深模块设计与架构深化

> 来源致谢：本文的"深模块/深化机会"纪律取精华自 **mattpocock/skills**（`codebase-design`、
> `improve-codebase-architecture`）并适配本技能，其底层原则源自 John Ousterhout
> *A Philosophy of Software Design*（深模块）。只内化纪律，不复制原文。

## 定位

技术债重构的**方向舵**：不仅"把大的拆小"，更要"把浅的做深"——让大量行为藏在小接口之后，
放在干净接缝上、可通过该接口测试。用于 Phase 0 审计的宏观信号与 Phase 3 拆分设计的取向。

## 深模块判据（interface ≪ implementation）

- **深模块**：接口小、实现承载多——调用方只需知道少量概念即可获得大量功能。**优先产出深模块**。
- **浅模块（债务信号）**：接口和实现一样复杂（pass-through 方法、getter/setter 堆砌、把复杂度
  原样透传给调用方）。审计时标记为**深化机会**。
- **信息隐藏**：把设计决策/易变知识藏在模块内；泄漏到接口的实现细节是抽象泄漏债。
- **接缝（seam, Michael Feathers）**：模块边界应落在依赖最少、语义最内聚处，且能从接口一侧测试。
- **删除测试**（The Deletion Test）：假设删掉该模块——若复杂度消失，说明它是 pass-through；若复杂度重新分散到 N 个调用方，说明它正在发挥价值。
- **一个 adapter = 假想接缝，两个 adapter = 真实接缝**：别在无真实变化的地方引入接缝。
- **把错误设计消失**：能通过接口设计让某类错误“不可能发生”的，优先于到处 try/catch。

## 架构深化审计（improve-codebase-architecture 取向）

Phase 0 宏观扫描时，除循环依赖/god-class/分层违规外，追加**深化机会**清单：

| 深化信号 | 表现 | 深化动作（Phase 3 取向） |
|---------|------|------------------------|
| 浅模块 | 接口与实现同复杂、pass-through | 合并/下沉逻辑，收窄接口 |
| 抽象泄漏 | 调用方必须懂内部才能用对 | 把知识收回模块内，重定义接口 |
| 时序耦合 | 必须按隐含顺序调用 | 用接口约束/合并为单一入口 |
| 配置扩散 | 同一决策散落多处 | 收敛到单一深层默认 |

> 深化是**调查而非救援**（a survey, not a rescue）：审计只产出候选 + ROI（复杂度降幅 × 影响面 × 近期变更频率 hot-spot 加权），是否深化仍走 G0 用户确认。

**范围先行（scope before scan，YAGNI）**：深化某模块回报在于让对它的未来修改更容易，故走 `git log --oneline` 找 hot spot（频繁变动的区域）作为扫描重心，而非无差别全量扫描。

## 与本技能工作流的挂接

- **Phase 0 审计**：宏观信号追加"浅模块/抽象泄漏/深化机会"，纳入 P0-P3 分级与 ROI。
- **Phase 3 拆分设计**：拆分取向为"产出更深的模块"，而非仅按行数切割；接缝落在可测试边界。
- **关键原则**：深模块优先——"把浅的做深"与"把大的拆小"并列，且前者常更降复杂度。

## 禁止

- 不为"深"而过度设计：深模块的目的是降复杂度，不是堆抽象层。
- 不改可观察行为（沿用本技能"行为不变 + 安全网 + 小步可回退"铁律）。
