# REFERENCE-FALSE-SUCCESS — 假成功甄别体系

> 存量系统深度验收最大的敌人：**看起来通过但实际是错的**。本文档是假成功的完整分诊体系。
> 实证背景：后端 DB 访问代理（dbserver 类）吞 SQL 异常统一返 200+空/null，接口层无法区分
> "合法空"与"吞错"，曾致 4 个"数据空需造数"误判（实为三表全库不存在）。

## 一、响应体六态分诊（bodyVerdict）

一切断言/探针**先分诊再定性**。对捕获的 API 响应 `{ hits, status, body }`：

| 态 | 判定 | 含义 |
|----|------|------|
| `no-hit` | 无命中 | 接口未发起（自动查询页可能是时序问题，用 waitForHit 兜底） |
| `http:N` | status ≥ 400 | HTTP 层失败（真失败或间歇抖动，按豁免规则甄别） |
| `code:500` | HTTP 200 但 body.code='500' | **吞错态**——后端业务异常被包装成 200 |
| `result:null` | HTTP 200 但 result 缺失/为 null | **吞错态**——但对部分写接口是合法空返回，需结合语义 |
| `empty` | result 为空数组/空对象 | 合法空 or 数据问题——走三分法（下节） |
| `data` | 有数据 | 唯一可以直接判 pass 的态 |

**铁律**：`code:500` 与 `result:null` 属吞错家族（非合法空）；monitor 只捕 HTTP≥400，
code:500-in-200 **不会**进 apiFailures——依赖查询结果的用例必须用 captureApis/bodyVerdict
主动断言，不能指望 noErrors 兜底。

## 二、假成功嗅探（框架内置，只观测不改判定）

monitor 对 `config.businessApiPattern` 匹配的 JSON 响应自动嗅探：HTTP 2xx 但 body
`code!=200` 或 `result:null` 时记入 `collect().swallowed`，run.js 自动附到报告
`[假成功嗅探]` 段（去重同 URL+kind，最多 10 条）。

设计约束：
- **只观测不改判定**——result:null 对部分写接口合法；
- 看到嗅探段必须人工甄别"合法空 vs 吞错"后再写结论；
- 用例导航后才 `monitor.reset()` 时导航期嗅探被清零（设计内，同 apiFailures 语义）。

## 三、开测前预检（precheck，把假成功消灭在源头）

`node run.js <module> --precheck`：从 registry 顶层 `backend_mappers` 扫 SQL/mapper 文件，
四段检查（详见 SKILL.md Phase 2）：

1. **方言静态扫描**（纯静态不依赖 DB）：目标 DB 不支持的方言形态高置信计入退出码。
   典型 PG→Oracle 形态：`over(partition by)` 缺 order by（ORA-30485）、`::` 强转、
   `limit`、`ilike`、`now()`、`on conflict`、`string_agg`、`split_part`。
   **为什么必须静态扫**：空表时 join 短路不求值不报错（接口 200+空，伪健康），
   造数后才真正求值引爆——不预扫会逐页暴雷，代价是多次部署。
2. **表存在性批扫**：`FROM/JOIN/INTO/UPDATE/DELETE FROM` 抽取物理表（剔除 CTE/关键字），
   ↔ `all_objects` 比对。缺表 → 吞 ORA-00942 返空 → 预判 blocked。
3. **自定义函数存在性**：`f_/fn_` 前缀引用 ↔ FUNCTION/PROCEDURE/PACKAGE。缺函数命中
   SQL 整条被吞。
4. **列存在性**：`alias.col` ↔ `all_tab_columns`，**仅对无歧义别名直连物理表判缺，
   宁漏勿误报**。"表在、列缺"是最阴的 schema 漂移（有数据仍空/500）。

退出码：0 全过 / 3 有缺失项或高置信方言（预判 blocked，勿直接造数）/ 2 预检自身故障
（含 DB 通道不可用，此时静态方言段仍落盘报告）。

**复杂 SQL 被吞的定位利器——拆段二分重放**：core where → 逐 join → 逐函数列/子查询列，
用 DB 直查通道逐段加回重放（某段一加回就返空=命中吞错段），几轮锁定坏点。
一页叠多个根因（表缺+函数缺+列缺+方言）时这是唯一有效路径（服务日志常不可达/吞栈）。

## 四、统计/报表页 200+空 三分法

接口 200 + 空数组 ≠ 直接判"需造数"。先用 DB 直查源表区分：

- **(a) 日期默认过窄**：页面默认查昨天，`group by trunc(stat_date)` 看分布发现数据在
  历史快照日 → 驱动用例到有数据日期可验（可 pass 或合法空）；
- **(b) 组织域不匹配**：统计查询 join 组织域表，登录账号不在其内，`group by mgt_org_code`
  发现数据挂在触达不到的分支 → 数据类 blocked；
- **(c) 源表真空** `count(*)=0` → 需造数。

三类均先验查询链路本身（200/空态渲染/筛选重置/无 JS 错），registry 执行注写明
具体表名+日期/组织实证。**"数据空需造数"结论必须先过表存在性校验，否则造数白跑。**

## 五、疑似入库断链判定（日志/流水类页面）

操作日志、升级历史、审计日志、接口日志等**记录类页面**：

- **200+空数组 ≠ pass-empty**——大概率是写入端断链（序列缺失/列宽超限/代理吞异常假成功）；
- 处置：registry 标 blocked，reason 写"疑似入库断链"；
- 判定辅助：触发一次应产生日志的操作 → 复查是否有增量（探针模式：登录→触发写入→查库 diff）；
- 普通业务查询页的 200+空走第四节三分法，合法空可 pass-empty 并注明。

## 六、假失败甄别（反向陷阱）

- **90001/非 200 code 先判真假失败**：①假失败——返错误码但主操作已生效（日志写入失败+
  回滚被注释）；②真失败——错误码且未落库。对策：写操作断言一律以 list 复查/DB 直查为准，
  探针直调+复查区分；UI 行文本有渲染时序误判，以接口响应体字段为准。
- **导出类**：前端响应拦截器对 Blob 按 JSON 校验报的 console.error 是假失败，
  以 download 事件/Blob 响应为准。
- **间歇 500/404**：只有"重试成功"才豁免——URL 命中豁免表且同路径稍后 2xx 才记 exempted；
  持续失败照常 FAIL；每条豁免必须写明"为什么不是本页缺陷"。
- **全量连跑的 FAIL 先单跑复验再定性**：连跑环境叠加易抖动，终态以单跑/分批稳定态为准；
  后端问题用 curl 直调 3 次稳定复现才定性（区分 token 失效 500 与业务 500）。

## 七、body-code:500 归因的"正负对照行"实验

接口 HTTP200+code:500 时，区分"造数不完整可修"与"后端行处理缺陷不可修"：

1. 找同域能返 code:200 的对照行（其他种子/存量数据）；
2. 逐批对齐自己种子的差异字段（组织→日期→引用→其余列）每轮重探；
3. 全部对齐仍 500，且对照行也从未被观察到"返回行+200"（恒 total:0）→ 实锤
   "命中行→500，不命中→200/0"，500 在结果行处理路径，非造数可解，登记 pending 标 blocked。

**数据假设最多证伪 3 轮**，超过转入 blocked 流程。
